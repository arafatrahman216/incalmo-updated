1. PROPOSAL GROUPINGS (the shared intuition)
================================================================================
Per the user, the six proposals cluster into two families plus one glue piece:

  GROUP A — "World model" (state/knowledge centric): Proposals 1, 2, 5
      Shared goal: give the planner an ACCURATE, COMPLETE, PERSISTENT model of
      the network and of what still needs doing, so it neither (a) stops early
      nor (b) acts blind to where it is.
        - P1 Goal-and-Progress Manager  -> explicit goals + completion gate
        - P2 Location-Aware Attack Graph -> reachability conditioned on vantage
        - P5 Structured 4-Tier Memory    -> confidence/TTL/failures/hypotheses
      They reinforce each other: P1's coverage oracle is more accurate with P2's
      reachability; P5 supplies the confidence/failure data both consume.

  GROUP B — "Planning & execution control": Proposals 4, 6
      Shared goal: stop betting the whole run on one sequential path; explore
      alternatives and run independent work concurrently.
        - P4 Bounded Beam Search  -> keep k candidate tasks, backtrack on failure
        - P6 Parallel DAG Scheduler -> run independent tasks simultaneously

  GLUE — Proposal 3 Verifier + Task Contracts
      Deterministic postcondition checks + structured failure classification.
      Feeds BOTH groups: it is what turns "command returned output" into
      "goal state actually changed", and it produces the failure classes that
      P5 stores and P4 uses to promote the next candidate.

2. HOW INCALMO WORKS TODAY (verified against the code, 2026-10-01)
================================================================================
STRATEGY LOOP  (incalmo/core/strategies/llm/llm_strategy.py)
  - run_incalmo_strategy() loops strategy.main() -> step() until it returns True
    or a 75-min cap (incalmo/incalmo_runner.py, TIMEOUT_SECONDS).
  - step(): refresh agents from C2 -> update_host_agents() -> llm_request().
  - Termination (llm_strategy.py:157, :228-229): loop ends when the LLM emits
    <finished> (LLMResponseType.FINISHED -> return True), OR cur_step >
    total_steps (=100), OR guardrail/empty/soft-refusal guards fire.
  - finished_cb() only logs/backfills — THERE IS NO COMPLETION VERIFICATION.
  - The LLM's only working memory across steps is self.last_response (previous
    action result) + whatever it re-queries. "Flat context."

KNOWLEDGE GRAPH  (incalmo/core/services/environment_state_service.py
                  + incalmo/core/models/network/*.py)
  - It is already a property graph, just thin:
      Nodes: Network -> [Subnet] -> [Host]
      Host(host.py): ip_addresses, hostname, users,
                     open_ports{port->OpenPort(service, CVE[])},
                     ssh_config[SSHCredential], critical_data_files{user->[f]},
                     agents[], infection_source_agent
      Edges: SSHCredential(credential.py) stored on the host that POSSESSES it,
             pointing at a target host_ip, with a `utilized` flag  => a
             credential edge holder->target. infection_source_agent = 2nd edge
             type (who infected whom).
  - Updates are purely event-driven: actions emit typed events
    (HostsDiscovered, ServicesDiscoveredOnHost, SSHCredentialFound,
     InfectedNewHost, CriticalDataFound, VulnerableServiceFound,
     ExfiltratedData) and parse_events() folds them in.
  - GAPS (= Proposal 5): no confidence, no timestamp/expiry, no
    hypothesis-vs-fact distinction, no record of FAILED attempts.
  - Statefulness: within a run the `network` object persists and accumulates;
    BUT StateStore.initialize() wipes at start (no cross-run memory), and
    update_host_agents() RESETS host.agents each step from the live C2
    (C2 = source of truth for agent presence).

ATTACK GRAPH  (incalmo/core/services/attack_graph_service.py)
  - NOT a stored graph — on-demand generators over the knowledge graph:
      get_possible_attack_paths(attack_host, target): edges from (a) creds
        attack_host holds to target, (b) each open port on target.
      get_possible_targets_from_host(...), get_attack_paths_to_target(...).
      find_exfiltration_path(target): recursive DFS over credential edges,
        base case host.has_service("http").
  - Only persistent state: executed_attack_paths[] (dedup log of what's tried);
    already_executed_attack_path() does fuzzy same-target+same-technique match.
  - CRITICAL FLAW (= Proposal 2): reachability is GLOBAL and UNCONDITIONED.
    get_possible_targets_from_host (attack_graph_service.py:114) assumes any
    agent-bearing host can reach any target with an open port/cred. Only
    location concept is the boolean Subnet.attacker_subnet. No routing/firewall/
    ACL model. AttackTechnique carries no cost/utility/detection — the extended
    action model a:(s,o)->(s',r,c,d) from the deck is absent.

4. DESIGN PLAN (per proposal)
================================================================================
P1 — GOAL-AND-PROGRESS MANAGER  (Group A)
  - Add explicit Goal set to environment def (environment_initializer.py), e.g.
    ExfiltrateCriticalData(all), Compromise(role=db). Fallback when no ground
    truth: COVERAGE ORACLE = "no reachable, un-acted target remains".
  - Oracle reuses existing methods: remaining compromise =
    network.get_uninfected_hosts() with a non-empty get_attack_paths_to_target()
    from some infected host; remaining exfil = hosts with critical_data_files
    not in env.exfiltrated_data and reachable via find_exfiltration_path().
  - Gate at llm_strategy.py:157/:228. <finished> becomes a REQUEST: if
    goal_manager.unmet_goals() is empty -> finish; else reject, set last_response
    to a structured "goals remaining" message, force continue or evidence-backed
    infeasibility. max_rejections safety valve.

P2 — LOCATION-AWARE ATTACK GRAPH  (Group A)
  - ENABLER: vantage-tag observations. ScanReportEvent + scan actions must
    record which agent/host performed the scan; propagate into
    update_network_from_report() so each port/host carries "observed from X".
  - Add ReachabilityMatrix[source_host -> set(reachable_subnets)] populated from
    vantage-tagged scans. Condition get_possible_attack_paths /
    get_possible_targets_from_host (attack_graph_service.py:208, :114) to only
    emit an edge if attack_host can reach target's subnet.
  - Extend AttackTechnique toward (s,o)->(s',r,c,d): predicted goal_progress,
    cost, detection_risk, required privilege. Even static scores enable ranking
    by expected utility (also feeds P4).

P5 — STRUCTURED 4-TIER MEMORY  (Group A)
  - Enrich existing nodes/edges (don't replace): add to OpenPort/SSHCredential/
    CVE/critical_data_files -> source_agent, first_seen, last_seen,
    confidence(0-1), ttl, contradicted. Add `verified` to creds (session
    actually obtained) distinct from "found".
  - New stores on EnvironmentStateService:
      FailureLog[FailureRecord(action, source, target, failure_class, ts)]
        <- highest value / lowest effort; stops repeated-failing-action loops.
      Hypotheses (suspected vulns/routes; evict on contradiction/TTL).
  - Tiers: Facts / Hypotheses / Failures / Plans (deck slide 15).
  - Surface tiers in the prompt (get_infection_summary_str, llm_interface
    pre_prompt) — invisible state won't change behavior.

STATEFUL EXECUTION (foundation for P3/P4)
  - Per-step pre/post snapshots of the touched subgraph (Host.to_dict()+creds)
    -> powers P3 verifier diff and P4 backtracking.
  - Persist knowledge graph + executed_attack_paths + memory tiers to StateStore
    each step (keyed by task_id) -> resumable, auditable.

P3 — VERIFIER + TASK CONTRACTS  (Glue)
  - Stage 1 postcondition check: compare pre/post env snapshots to the task's
    declared postconditions (e.g. LateralMove succeeds ONLY if a new session/
    agent exists for target -> kills the "empty stderr = success" false positive).
  - Stage 2 structured failure classification (raw output never hits planner):
    wrong-target | insufficient-priv | unreachable | exploit-mismatch |
    tool-error | planner-logic-error -> each maps to a recovery action.

P4 — BOUNDED BEAM SEARCH  (Group B)
  - LLM proposes top k=3 candidate tasks + rationale; symbolic controller scores
    U(pi)=aG-bC-cD-dR and retains all k; on verified failure promote next-ranked
    (no full replan). Needs the candidate/backtrack layer over the sequential
    loop + snapshots from "stateful execution".

P6 — PARALLEL DAG SCHEDULER  (Group B)
  - Dependency model over tasks; dispatch independent tasks simultaneously
    (parallel subnet scans, multi-DB exfil, multi-host priv-esc); sync barrier ->
    verifier merge -> goal-manager coverage. Needs async orchestrator + C2
    command-model changes (today synchronous).

SUGGESTED BUILD ORDER
  1) Vantage-tagging + FailureLog (enabler plumbing)
  2) P1 GoalManager gate (max impact / least code; fixes reproducible failure)
  3) P2 location-conditioned reachability (the correctness win)
  4) P5 memory-tier enrichment + prompt surfacing
  5) P3 verifier/contracts -> then P4 beam, P6 DAG (Phase-3 architectural)

5. USER REQUIREMENTS  (BINDING — honor these in all implementation)
================================================================================
R1. CONFIGURABILITY: every proposal must be independently switchable via config
    (config/config.json). Must be able to run:
      - original/baseline Incalmo (all flags off),
      - any single proposal (e.g. only P1, or only P2),
      - any combination (P1+P2, P1+P2+P5, ...), up to all of them.
R2. DECOUPLING / NO HARD DEPENDENCIES: each feature is a self-contained module
    with a clean interface and GRACEFUL FALLBACK to baseline behavior when its
    flag is off. No feature may require another feature to be on to function.
    (Soft synergy is allowed — e.g. P1's oracle is more accurate when P2 is also
    on — but P1 must still work correctly with P2 off, using current global
    reachability.)
R3. INCREMENTAL, TESTED ONE-BY-ONE: implement and validate each feature on its
    own before combining. Each lands behind its flag without altering baseline.
R4. MANUAL TESTING via HAND-CRAFTED ATTACK GRAPH: the supervisor asked for
    manual testing by manually crafting the attack graph. Provide a way to
    inject a hand-made environment/attack graph (no LLM, no Docker) and run the
    feature logic against it deterministically.
R5. Keep this file updated with every major decision (section 7).

RECOMMENDED APPROACH (agreed direction — see decisions log):
  - Assign Claude to modify the code, adding each proposal behind an independent
    config flag, built & tested one at a time, starting with P1.
  - ALSO build a manual fixture harness (R4): a JSON/YAML describing subnets,
    hosts, ports, CVEs, creds, agents, and a reachability matrix; a loader that
    constructs the Network + seeds EnvironmentStateService/AttackGraphService
    with NO LLM and NO Docker; then unit/scenario tests assert each feature's
    behavior (e.g. GoalManager refuses <finished> while DB reachable;
    location-aware graph hides unreachable DB from a given vantage).
  - Rationale: P1/P2/P5 core logic is pure functions over the graph, so manual
    injection fully validates them cheaply; P4/P6 also need a mock planner/
    executor but the same fixtures drive them.

FEASIBILITY ANSWER (to "is it possible?"): YES.
  - Config-flag + decoupled modules with fallback: standard, fully achievable.
  - Manual attack-graph injection for testing: achievable and recommended as the
    primary validation path for Group A; combine with occasional full LLM+Docker
    runs for end-to-end confirmation.
